# Multiplayer visibility updates

Custom matches negotiate snapshot protocol 2 when creating, joining or resuming a room. An initial or reconnect snapshot always contains complete visibility and exploration grids. Subsequent snapshots carry changed visible cells and newly explored cells, plus a sequence number. The client reuses its typed grids instead of allocating two full arrays for every update. Noncustom matches and clients that omit the capability retain full grids.

Visible cells encode `cell * 2 + value`; explored cells only transition to explored. The server advances the baseline and its resource cache only after a snapshot is accepted by the WebSocket send queue. A snapshot skipped because of queued traffic cannot consume visibility changes or resource patches. A large reveal uses full grids when the estimated JSON delta would be larger.

The receiver validates the entire delta before changing either grid and requires the next sequence. An invalid or missing update requests one resync and leaves the displayed match at its last accepted state. The server's resync includes full grids and all currently visible resource quantities, including updates the client may have missed. Reconnection starts from a full snapshot and negotiates capabilities again, including upgrades and downgrades between client versions. Hidden units and enemy treasuries still pass through the existing server perspective filters.

This design uses WebSocket's ordered delivery within one connection, described in [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.4). The sequence guards against application-level omission and stale baselines; it does not replace TCP. The queue limits follow the need to control buffered traffic described in the [WebSocket Standard](https://websockets.spec.whatwg.org/#dom-websocket-bufferedamount). Compression remains configured separately: [ws documents its CPU and memory costs](https://github.com/websockets/ws/blob/master/README.md#websocket-compression). Smaller JSON sizes are not equivalent to the same reduction in compressed wire traffic or frame time.

## Verification

`node --test --test-concurrency=1 tests/network-visibility.test.js tests/network-client.test.js tests/visibility-network.test.js tests/network.test.js tests/custom-network.test.js tests/projectile-network.test.js tests/deployment.test.js` covers the real client, mixed protocol versions, an eight-kingdom Huge map, allied scouting, enemy privacy, disappearing visibility, retained exploration, skipped server snapshots, resource recovery, reconnect and observer transitions.

`node scripts/visibility-multiplayer-qa.mjs` serves the production build on an isolated local server. It joins a rendered landscape-phone client to a legacy host, verifies allied scouting and actual client recovery after deliberately omitting one application state, issues paid training through the touch UI, reloads/rejoins, and checks the 844 × 390, 568 × 320 and 1366 × 768 layouts. It writes screenshots and a report under `artifacts/visibility-multiplayer`. `QA_BROWSER_ENDPOINT` can select an existing local CDP browser. This is browser/viewport emulation, not sustained physical-phone performance evidence or a hosted capacity test.

The targeted eight-kingdom stationary fixture measured approximately 32 KB per JSON state against 192 KB for the same state with full fog grids, before WebSocket compression. Actual payloads depend on entities, scouting and visible resource changes. The release records full regression, build and browser results in [the verification artifact](artifacts/visibility-verification-20261024.json) and [browser report](artifacts/visibility-multiplayer/report.json). The remaining game-wide acceptance requirements stay in [QUALITY_TARGETS.md](QUALITY_TARGETS.md).
